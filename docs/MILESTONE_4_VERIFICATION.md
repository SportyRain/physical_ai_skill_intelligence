## Scope

Milestone 4 adds only software-level failure-aware recovery decision logic:

```text
Goal
+
Current World State
+
Observed Failure
+
Candidate Existing Recovery Actions
+
Past Recovery Experience
        |
        v
Recovery Outcome Estimation
        |
        v
Recovery Ranking / Selection
```

This milestone does not add robot motion, a new planner, a new controller, LLM orchestration, RL, IL, VLA, ROS execution, or real UR3 execution.

Existing UR3 repositories remain stable skill providers. No provider repository was modified.

## Exact failure/context matching

Recovery evidence matches only when all of the following are exact:

```text
goal predicate
state context
failure code
failure attribution
recovery action
```

`UNKNOWN` is literal data and is never treated as a wildcard.

A recovery candidate is considered only when:

1. its explicit `failure_codes` contains the observed failure code; and
2. its declared state preconditions are satisfied.

A missing/unknown state fact fails precondition matching through the existing fail-closed `WorldState.satisfies` behavior.

## Recovery outcome estimator

The first recovery estimator remains an inspectable deterministic baseline:

```text
Beta(1,1) prior
P(recovery_success | goal, state, failure, recovery_action)
mean recovery cost
recovery evidence count
uncertainty
provenance trace
```

No recovery evidence uses the explicit prior:

```text
P(recovery_success) = 0.5
method = explicit_beta_prior_no_recovery_evidence
```

This is not claimed as a novel AI algorithm.

## Ranking policy

Applicable recovery candidates are ranked deterministically by:

1. higher estimated recovery-success probability;
2. lower observed mean recovery cost plus declared nominal recovery cost;
3. lower uncertainty;
4. stable declared candidate order as final tie-break.

No robot command or low-level trajectory is generated by the decision layer.

## Tests added

`tests/test_recovery_decision.py` verifies:

- no recovery evidence uses an explicit deterministic prior;
- same recovery input produces the same decision;
- recovery experience can change recovery selection;
- a different failure code does not silently match;
- a different failure attribution does not silently match;
- `UNKNOWN` failure is not a wildcard;
- failure code filters recovery candidates;
- recovery preconditions fail closed;
- duplicate recovery experience is idempotent;
- conflicting duplicate recovery identity is rejected.
